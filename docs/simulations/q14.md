# Вопрос 14: воспроизводимый учебный стенд

## Задание и границы допуска

Поручение владельца от 20.10.2026: подготовить полную симуляцию ситуации вопроса 14
в раннерах через PR с ИИ. Каноническая передача работы находится в PR этой ветки;
новая параллельная задача или производственная подсистема не создаётся.

- База: `develop` `d6f5cafbfcb337006444177d8f15400ab4ddb274`.
- Ветка: `feat/q14-ai-simulation`; один исполнитель реализации: ChatGPT,
  область ответственности: тесты и CI учебного стенда.
- Контракт реализации: 12 сценариев с журналом событий, отрицательный контроль,
  ограниченный ИИ-разбор «обвинение / защита / проект решения», раздельные
  доказательства локального теста, раннера, API и пользовательской приёмки.
- Доступ: чтение исходников; изменения только в ветке/PR; использование уже
  добавленных `YANDEX_API_KEY` и `YANDEX_PROJECT_ID` только в provider-шаге.
  Секреты не изменяются, не передаются в промпт и не публикуются.
- Стадия: реализация и детерминированная проверка. Оплачиваемая генерация ожидает
  отдельного подтверждения бюджета. Модель не назначается Логосом и не получает
  права суда, merge, управления устройствами или исполнения собственных ответов.
- Стоп: отсутствие ключей/одобрения, HTTP-ошибка, тайм-аут, неверная схема ответа,
  превышение лимита входа. Повторов, эскалации модели и автоматического merge нет.

«Полная» здесь означает воспроизводимый цикл внутри объявленного набора сценариев,
а не исчерпывающую модель электротравмы или всех электроустановок. Это не инструкция
по переключениям. Фотография, ФИО, адрес внутренней системы, логины и пароли в стенд
и запросы к модели не включаются. Реальный ущерб всегда остаётся `NOT_ESTABLISHED`.

## Три разных уровня

1. `q14_simulation.py`: конечная логическая модель, входные события, защита и
   проверяемые исходы. Заданное исключение АРМ не означает, что оно применимо на объекте.
2. `q14_ai_review.py`: три последовательных, ограниченных запроса к одному Yandex
   backend `logosai-llm-flash`. Это не три независимых эксперта. Каждый этап разбирает
   все 12 сценариев, возможных потерпевших, основания ответственности, исправления
   и неопределённость; ссылается на идентификаторы событий своего сценария.
3. Человеческое содержательное ревью и приёмка: не выполняются автоматически.
   Совпадение исходов и валидный JSON не доказывают правильность всей прозы модели.

Метод обвинение → защита → суд взят из [#1420](https://github.com/maksimp6/Chat/issues/1420).
Там обсуждается другой билет: вариант 4 из #1420 не переносится в вопрос 14.
Правовые предпосылки ограничены предыдущим разбором пп. 16.1, 19.1, 19.6, 20.1–20.2
[приказа 903н](https://publication.pravo.gov.ru/Document/View/0001202012300142)
с указанием [изменения 287н](https://publication.pravo.gov.ru/document/0001202505300025).
Раннер не перепроверяет действующую редакцию закона и ключ экзаменационной системы.

Образы ангела, посланника, духа, Бога, ада и рая сохранены в `CONTEXT` как явно
предлагаемые интерпретации, не новые нормы проекта. Ева обозначает метод разбора;
backend не присваивает полномочия Евы или Логоса. Никакой символ не расширяет права.

## Набор сценариев

| ID | Входная ситуация | Ожидаемый исход ограниченной модели |
| --- | --- | --- |
| S1 | Основной порядок, исправные предпосылки | MODEL_ACCEPTED |
| S2 | Напряжение осталось после команды отключения | BLOCKED |
| S3 | Заземление до проверки | BLOCKED |
| S4 | Поздние запреты без условий АРМ | BLOCKED |
| S5 | Тот же порядок при заданных условиях АРМ | MODEL_ACCEPTED |
| S6 | Заявление «готово» без действий | BLOCKED |
| S7 | Непригодное доказательство отсутствия напряжения | BLOCKED |
| S8 | Отрицательный контроль: барьер отключён, напряжение осталось | HAZARDOUS_OPERATION |
| S9 | После проверки напряжение появилось вновь | BLOCKED |
| S10 | Допуск без завершающих мер | BLOCKED |
| S11 | Подготовка оборвана | INCOMPLETE |
| S12 | Неизвестное событие | ERROR |

Ожидаемые исходы не передаются в промпт. После третьего ответа они сравниваются
с классификацией модели отдельно. Расхождение сохраняется как `AI_REVIEW_DISAGREES`,
без автоматической платной «починки». Отрицательный контроль проверяет именно
возможность обнаружить опасную операцию, а не способность всегда выводить успех.

## Запуск и одобрение расходов

Детерминированная проверка без зависимостей и сети:

```bash
python -m unittest discover -s tests -p test_q14_simulation.py -v
python -m scripts.q14_ai_review --mode offline --out q14-offline
```

При открытии/изменении авторского PR этой ветки раннер после тестов выполняет только
`GET /v1/models`. `MODEL_CATALOGUE_READ` означает чтение каталога, **не подтверждение
генерации, тарифа, баланса или полного набора прав ключа**. Нет запросов к платной
генерации, пока отдельно не одобрен бюджет.

Готовый лимит одного ИИ-прогона: максимум 3 последовательных POST-запроса, до 4096
выходных токенов и 48000 символов входных данных на запрос; сетевой тайм-аут 90 секунд.
Входной лимит не включает фиксированную короткую системную инструкцию. Это технические
ограничения, **не жёсткий рублёвый потолок**. Цена и окончательное списание неизвестны;
`provider_confirmed_spend` и `hard_currency_cap` равны `null`, а не нулю. Автопополнения нет.

После ознакомления с этими ограничениями владелец может явно одобрить один прогон:
добавить к PR метку `q14-ai-approved-3-calls` либо вызвать workflow с `mode=live`,
`approved_calls=3` и ссылкой `approval_reference` на своё одобрение. До слияния
нового workflow доступен путь через событие метки PR; кнопка workflow_dispatch
может отсутствовать, пока файл не попал в default branch. Агент не добавляет метку
вместо владельца без его явного одобрения бюджета. Триггер live допускается только
от владельца; наличие метки на последующих push не запускает генерацию повторно.

Повторное добавление метки или новый ручной dispatch означает **новый платный прогон**.
Rerun существующего run не запускает provider-job. При неизвестном результате POST
нужно сначала исследовать сохранённый request/response ID и ledger, а не повторять.
Один concurrency group исключает одновременные запуски этого стенда для одного PR;
это не утверждение об общем лимите расходов всего аккаунта.

## Доказательства и проверка

Артефакты `q14-offline-<run>-<attempt>` и `q14-provider-<run>-<attempt>` содержат:
`manifest.json` (точный checkout SHA и run ID), `simulation.json`, `context.json`,
`report.md`, `sha256.json`; provider дополнительно `access.json` либо `ai-ledger.json`,
ответы этапов и `ai-comparison.json`. Промпты не сохраняются; ответы содержат только
учебные данные и дополнительно очищаются от известных значений секретов.

Проверить содержимое после загрузки артефакта, а не только зелёную иконку:

```bash
python - <<'PY'
import hashlib
import json
from pathlib import Path
root = Path('q14-offline')
for name, expected in json.loads((root / 'sha256.json').read_text()).items():
    assert hashlib.sha256((root / name).read_bytes()).hexdigest() == expected, name
manifest = json.loads((root / 'manifest.json').read_text())
print(manifest['checkout_head'], manifest['run_id'], manifest['status'])
PY
```

`sha256.json` не включает собственный хэш; общий digest ZIP выдаёт GitHub.
Норма владельца по отчётности CI не меняется. Ни статус job, ни совпадение хэшей
не равны безопасности реального объекта, независимому ревью текста или приёмке.
Локальные ответы-заглушки в тестах никогда не выдаются за работу Yandex API.
