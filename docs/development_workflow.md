# Рабочий процесс разработки Logos

Действующая редакция: 27 октября 2026 года. Для новой работы сначала читать
[AGENTS.md](../AGENTS.md) и применимые локальные инструкции. Новое прямое
распоряжение владельца определяет исключение в пределах указанного им действия;
остальные разрешения не возникают автоматически.

## 1. Публикация и проверка

Обычный маршрут разработки:

1. Уточнить проверяемый результат по задаче и существующим материалам.
2. Прочитать актуальные инструкции, проверить `develop` HEAD и наличие уже
   выполняемой реализации.
3. Внести связанное изменение, прочитать diff и получить независимое ревью,
   исправить обнаруженные замечания.
4. Опубликовать прямым `push` в `develop` и проверить, какой коммит находится
   в удалённой ветке. Перед публикацией учесть новое продвижение `develop`,
   сохранив чужие изменения; force-push не выполнять.
5. Отдельно зафиксировать доказанный результат, ограничения и статус приёмки.

Промежуточные ветки и PR не создавать, merge вместо push не выполнять. Если
прямой push недоступен, сообщить конкретный блокер. Не обходить его через PR,
изменение защиты или запись в `master`. Команды продолжения сохраняют этот
маршрут. `master`, deploy и merge требуют отдельного распоряжения владельца.

Тесты, тестовые сборки и тестовые workflow без отдельной команды пользователя
не запускать. При явном поручении тестирования разрешены только оговорённые
проверки внутри задания GitHub Actions runner. Не подменять признаки runner в
среде ради обхода локального запрета. Само наличие runner не разрешает запуск.
Непроведённые проверки отмечать `NOT_RUN`; чтение diff не выдавать за тест.

Обычная публикация также не разрешает вызов модели, изменение доступа или
секретов, платную операцию, deploy либо отмену судебного запрета D0. Для каждого
такого действия действует его собственный допуск. Наличие задания в Actions не
доказывает успешность сценария; если автоматическое задание уже возникло,
чтение его статуса не означает разрешения на повторный запуск.

## 2. Ответственность и начало работы

Владелец определяет цель, приоритеты, существенные изменения и приёмку.
Исполнитель отвечает за актуальное состояние исходников, реализацию,
статическое ревью, исправления и честный отчёт о результате. Независимый
проверяющий не принимает собственное исправление от имени другой роли.

Перед изменением зафиксировать:

- проблему и ожидаемое наблюдаемое поведение;
- текущую версию источников и затронутые файлы;
- существующего исполнителя, задачу и границы полномочий;
- сценарий проверки и разрешён ли его запуск;
- конкретные зависимости и блокеры.

Например: после двух фактических tool calls Trace должен содержать оба вызова,
их аргументы, результаты и статусы, а ответ пользователя должен сохраниться.
Описание этого критерия не означает, что вызовы уже выполнены или разрешены.
Независимые участки можно распределить между исполнителями с непересекающимся
владением файлами; второй ремонт той же проблемы не создавать.

## 3. Критерии завершения

Отдельно сообщать:

- **Реализовано:** изменение опубликовано на указанном SHA, документация
  соответствует коду, статическое ревью завершено или имеет точный блокер.
- **Проверено:** перечислены фактически проведённые разрешённые проверки,
  их версия, входы, наблюдаемый результат и предел доказательства. Для остальных
  проверок — `NOT_RUN`, без ложного PASS.
- **Приёмка:** решение владельца указано отдельно; публикация коммита,
  HTTP 200 и зелёный CI её не заменяют. «ОК» означает приёмку этапа, не merge.

Отсутствие отдельной команды тестирования не препятствует разрешённой
публикации, но не позволяет назвать поведение проверенным. Сценарии, которые
требуют отдельного допуска, остаются открытыми с конкретным следующим шагом.
Для дел Суда применяется [процедура рассмотрения](agents/logos-court-procedure.md)
в каноническом [деле #1413](https://github.com/maksimp6/Chat/issues/1413).

## 4. Инструменты и Execution Trace

Для каждого локального или MCP-инструмента:

- успешный результат не содержит скрытую ошибку;
- ошибка инструмента возвращается вызывающему контуру;
- исключение отражается в `ExecutionTrace.errors`;
- фактический вызов сохраняется в `ExecutionTrace.tool_calls` с результатом,
  ошибкой и временем выполнения;
- пользовательский ответ не утверждает успех при ошибке или отсутствии вызова.

Несколько обращений Responses API внутри одной пользовательской операции
относятся к одному Execution Trace. Самоотчёт модели не заменяет события
исполнителя и наблюдение итогового состояния.

## 5. API-контракты и источники доказательств

HTTP API использует явный именованный контракт request, success-response и
error-response; источник формы не должен расходиться между route, frontend и
проверками. Типы, required/nullable поля, неизвестные поля и enum-значения
определяются в одном контракте. Сценарии отрицательной проверки описывать вместе
с изменением, а выполнять только при отдельном разрешении на тестирование.
Подробности: [API Contracts](api/contracts.md).

GitHub хранит разные виды сведений:

| Источник | Что он подтверждает |
| --- | --- |
| Issue и решения владельца | Цель, допуск, критерии, блокеры и изменение направления |
| Коммит на точном SHA | Опубликованную редакцию исходников |
| Исторический PR | Обсуждение и изменение в его собственных head/base, без нового разрешения на PR |
| Run / CI | Результат конкретного выполненного задания и его пределы |
| Execution Trace | Зафиксированные технические события, требующие проверки полноты |
| Документация | Правила и контракты с указанной областью и датой |

Успех одного источника не подменяет остальные. Для отмены дефекта кода
предпочитать отдельный обратный коммит в `develop`, сохраняющий историю и чужие
изменения. Разрушительные операции, изменения схемы данных, доступа или
production-инфраструктуры требуют соответствующего отдельного допуска.

## 6. Архив процедур PR / CI / merge

[Предыдущая редакция этого документа на SHA 5a5112ca8a62e33bb589404297f592055ec18a72](https://github.com/maksimp6/Chat/blob/5a5112ca8a62e33bb589404297f592055ec18a72/docs/development_workflow.md)
содержит прежние процедуры feature-веток, PR, локальных тестов, merge-readiness
и продвижения в `master`. Это архивный срез, доступный для разбора исторических
работ; он не задаёт маршрут новой разработки и не доказывает наличия прежних
workflow в сегодняшнем HEAD. В нём перечислены команды и инфраструктура,
которые могли быть удалены или отменены.

Исторические решения, включая [репетицию суда PR](../.github/agent-handoffs/pr-court-yandex-smoke.md),
оцениваются по правилам, действовавшим на дату конкретного события. Новую
редакцию AGENTS.md нельзя применять задним числом как основание обвинения.
Старое разрешение на один runner/model run не является постоянным допуском.
