# Рабочий процесс разработки Logos

## Начало задачи

Прочитайте [AGENTS.md](../AGENTS.md) и последнее прямое поручение владельца.
Порядок публикации и разрешение на проверки определяются ими; этот документ
не вводит дополнительный маршрут или обязательные CI gates.

Перед изменением зафиксируйте текущий `develop` и HEAD рабочей ветки или PR,
если они используются в поручении. Проверьте существующие Issues/PR, чтобы
продолжить нужную работу без дублей.

В канонической задаче должны быть цель, один основной исполнитель, критерии
приёмки, ссылки на точные исходные материалы и известные блокеры. Передавайте
независимые части работы с явным результатом и границей ответственности.

## Изменение и ревью

1. Выполните согласованное изменение в выбранном по поручению месте.
2. Прочитайте итоговый diff: проверьте объём, ссылки, совместимость данных,
   секреты и влияние на Execution Trace и учёт стоимости.
3. Исправьте найденные ошибки. Если другой исполнитель изменил базу,
   сопоставьте новый HEAD перед публикацией.
4. Опубликуйте результат по разрешённому маршруту и запишите точный SHA.
5. Для PR укажите поведение, причину изменения, фактическую проверку и ограничения.

`develop` — интеграционная ветка; `master` — личная ветка владельца.
Приёмка этапа «ОК» и разрешение на merge являются отдельными решениями.
Не меняйте защиту веток или историю ради публикации.

## Проверки

Тесты кода выполняются только по отдельной команде владельца и только внутри
GitHub Actions runner, согласно [AGENTS.md](../AGENTS.md). Эта инструкция сама
не запускает тесты, сборки, smoke или E2E. Не подменяйте переменные окружения runner.

Если проверки не запускались, результат — `NOT_RUN`. При разрешённом запуске
запишите команду, SHA, run/job, исходный результат и область проверки.
Длительность, exit code или зелёный статус сами по себе не подтверждают
пользовательский результат.

Прочтение diff и сверка ссылок подтверждают соответствующие свойства документов;
они не подтверждают исполнение приложения.

## Доставка и данные

Приложение используется через браузер. Обновление Redmi 9 выполняет существующий
runner: [сервер приложения](redmi-app-server.md) и
[порядок обновления](setup/redmi9-auto-update.md).

Для состояния приложения действует [контракт Kristall](database.md).
Учитывайте сохранение журнала и ключа шифрования; откат кода не является
восстановлением данных. Изменение журнала или production cutover требуют
соответствующего поручения.

## Завершение этапа

Отчёт содержит сделанное, SHA/PR, доказательства с их областью действия,
`NOT_RUN` и оставшиеся блокеры. Видимый результат на устройстве и
пользовательская приёмка фиксируются отдельно. Успешный commit, merge или
HTTP-ответ не закрывает автоматически критерий доставки владельцу.

См. также [выпуск](release.md), [интеграцию](development/develop-integration.md)
и [роли разработки](agents/role-based-agent-office.md).
