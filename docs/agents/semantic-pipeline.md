# Task-history search and semantic citations

Canonical task: #1413. Implementation: PR #1435,
`scripts/semantic_pipeline.py` and `.github/workflows/semantic-work.yml`.

## Source finding

`--corpus tasks` searches the title and complete body of every open and closed
Issue, excluding pull requests. `--corpus dialogues` retains the labelled
`rag-source` dialogue corpus and its header extraction, also including closed
sources. Search mode defaults to task history; query/red retain the dialogue
default. The manual workflow defaults to task-history search.

`--mode search` uses BM25 without calling a model, even when model credentials
or an allowance flag are present. It returns `RETRIEVAL_ONLY` and
`assessment: NOT_ASSESSED`, or `NO_CANDIDATES` when no match was found.

```sh
python scripts/semantic_pipeline.py --mode search --corpus tasks --query "Work Coordinator"
```

Every page uses `state=all`, ordered by creation, until an empty page. Repeated
Issue IDs, invalid pages and resource/page limits fail explicitly rather than
reporting partial coverage as complete. The traversal is not an atomic repository
snapshot: concurrent source changes remain possible.

An explicitly allowed model call in query/red mode can select candidates and
propose an answer. Mechanical checks establish only that a nonempty quotation
occurs in the specified candidate and source snapshot. They do not establish
relevance, semantic entailment, source truth or a real device outcome. Proposed
model claims remain `INSUFFICIENT_EVIDENCE`, with `semantic: NOT_PERFORMED`.
The search layer is not assigned responsibility for judging task completion.

## What was done and what remains

Results preserve GitHub `state`, `state_reason`, title, close/update times and
source identity. The summary counts open, closed/completed, closed/not_planned
and closed/duplicate separately. These are declared task states, not verified
completion counts. An open parent can have shipped prerequisites; a closed
duplicate or cancellation must not be counted as a delivered feature.

Read comments, linked PRs and current source code for relevant matching tasks
before concluding what was implemented, tested, cancelled, superseded or remains
outstanding. This index loads title/body only; the report declares
`comments: NOT_LOADED`, `linked_prs: NOT_VERIFIED`, `completion: NOT_ASSESSED`.
It does not claim a full execution audit of every indexed task.

## Evidence and outcomes

The report records source URLs, field and full-body SHA256, exact character
offsets, source update/retrieval times, corpus fingerprint and code SHA when
available. A title match has `field: title` with offsets/hash in the title;
a body match has `field: body` with offsets/hash in the complete body or extracted
dialogue text. Body citations also preserve their offsets in the full Issue body.

The fingerprint covers the complete fetched manifest, including state and
title/body identity. To bound output, `corpus_sources` lists matching sources;
`corpus_sources_total` and `corpus_stats` cover the full fetched corpus.
Search excerpts are bounded to 512 characters per candidate. Hashes identify the
fetched snapshot, not the future contents of an editable Issue.

Untrusted query, answer and quotations are displayed in a JSON fence longer than
every backtick run in the data. Structural status labels are generated by code.

| Outcome | Meaning |
| --- | --- |
| `RETRIEVAL_ONLY` | Search without a model call; no task-completion verdict |
| `CITATIONS_ONLY` | Citation identity checked; proposed claim remains unverified |
| `MODEL_REFUSAL` | An actual completed model call returned a consistent refusal |
| `NO_CANDIDATES` | BM25 found no candidates; the model was not called |
| `CONTRACT_VIOLATION` | Invalid query/schema/citation or RED nonrefusal; no publication |
| `PROVIDER_ERROR` / `TECHNICAL_ERROR` | Provider/transport failure; no automatic retry |
| `PUBLICATION_UNCERTAIN` | POST acknowledgement failed; inspect the Issue before retrying |

RED is `PASS` only after a model call returns a valid refusal. A search miss in
RED mode is `NOT_RUN`. Offline supplied-response tests prove the guard, not live
model behaviour. Provider response ID and usage are preserved when supplied;
unknown usage/cost remains unknown.

## Admission and bounds

Offline controls:

```sh
python -m pytest -q tests/test_semantic_pipeline.py tests/test_semantic_task_search.py tests/test_semantic_vector_store.py tests/test_semantic_workflow.py
```

The CLI does not call a model without explicit allowance. `--allow-model-call` is an admission
flag for query/red within an owner-approved scope and budget; credentials alone
are not approval. The manual workflow is owner-only, defaults to search without a model call,
and requires a budget approval reference when enabling a model call. There is no
Issue-label trigger or cancellation of an in-flight run in favour of a new run.
Both initiating actors must be the owner and only the first run attempt is
admitted. A new paid experiment requires a new explicit dispatch. The reference
records external approval; it is not a machine-enforced currency cap.

At most one model request is made. Input is bounded to 8,000 query characters,
60,000 prompt/instruction characters and 2,000,000 corpus title/body characters.
Output is bounded to 4,096 tokens and 262,144 response bytes. These are resource
limits, not a guarantee of price. Publication requires a positive Issue number and
token; an identifiable canonical receipt confirms the comment. No model or POST
retry occurs after an uncertain result.

No model call does not establish zero total cost. CPU, memory, storage, network,
runner resources, service quotas and the surrounding assistant work have not been
priced by this pipeline. The report keeps `cost: null` and
`cost_scope: total_execution_cost_not_measured`; it never reports total cost as zero
merely because the model was not called.

## Yandex AI Studio Vector Store demonstration

`--mode vector-store` is a separate owner-approved runner operation. It reads the
complete open and closed Issue corpus, preserving titles, full bodies and source
metadata. With `--include-repository`, it also reads every Git-tracked file from
the checked-out PR revision. UTF-8 text is indexed; binary files and symlinks are
represented by path, byte count and SHA256 only. Untracked/ignored files, comment
threads, pull-request bodies/reviews and credential-bearing files are excluded.
Known credential patterns in Issue and repository text are redacted before upload.

The deterministic repository Markdown file and Issue snapshot are uploaded
through the AI Studio Files API and attached to one repository-specific Vector
Store. This keeps the repository snapshot and task history together without
mixing their chunking metadata with the legacy task-history store. File and store
names are fingerprinted so a retry reuses them. Existing files are never removed
or overwritten. Each file remains bounded by the documented 128 MB limit.

After indexing, the runner makes one direct `vector_stores.search` request with
the maximum 50 results. It verifies exact search excerpts against Issue content
or repository-file text when the source path is present in the indexed chunk.
When `--allow-model-call` is also enabled, one `logosai-llm-flash` request to
Yandex's Responses API receives at most 12 retrieved excerpts, each capped at
2,500 characters. The input is bounded to 60,000 characters, output to 4,096
tokens, and the call is synchronous, non-stored and not retried. The model may
answer only from retrieved excerpts and returns their candidate IDs. The runner
copies exact quotes from those excerpts and verifies them against the indexed
source where possible. Semantic entailment is not assessed, so the generated
answer remains a proposal rather than a proven fact. Provider request ID and
usage are reported when returned; total cost is not measured.

The Yandex AI Studio API settings were checked against the official documentation
on 2026-10-21. Each snapshot file is capped at the documented 128 MB. The API
reference lists a static chunk maximum of 4,096 tokens and overlap no greater
than half the chunk size. Live attachment attempts at 4,096/2,048 and 4,096/2,047
were rejected with `CHUNKING_CONFIGURATION`, so the runner now uses 800/100, the
static settings shown in Yandex's official example. Store creation sends only a
name; chunking is configured on each attached file. The store name includes the
chunk settings. Yandex's file listing omits the accepted chunking strategy from
the attachment metadata, so the settings are known from the request rather than
an echoed response field. Direct search asks for the maximum 50 results, enables
query rewriting and the `auto` ranker, and uses a `0.0` score threshold to avoid
discarding lower-scored candidates. These recall-oriented settings can return
broader chunks and more ambiguous evidence than a tuned quality configuration.
The runner makes one search request. Text generation occurs only when explicitly
allowed by the workflow. It leaves file and store expiration unset, preserving
Yandex's documented default persistence for non-batch files and avoiding
automatic index expiry.

Embedding transparency: this runner uploads files to the managed Vector Store and
searches it; it does not call the standalone Embeddings API or pass an embedder
model URI, model version, or output dimension. Yandex describes AI Search indexing
as automatic, but the Vector Store API used here does not expose the exact internal
embedding model/version/dimension. Treat the embeddings as Yandex-managed and opaque:
do not identify them as `text-search-doc` or claim a vector size. Chunk size and
overlap above are text-splitting settings, not embedding dimensions; retrieval
scores are not an embedding-quality benchmark. The direct Embeddings API has an
optional `dim` field for models that support multidimensional outputs, but selecting
and recording it would require a separate embedding/indexing path.

References: [Yandex file upload API](https://aistudio.yandex.ru/ru/docs/ai-studio/api/Files/createFile),
[add a file to a Vector Store](https://aistudio.yandex.ru/en/docs/ai-studio/api/Vector-stores/createVectorStoreFile),
[search a Vector Store](https://aistudio.yandex.ru/en/docs/ai-studio/api/Vector-stores/searchVectorStore),
[AI Search indexing overview](https://aistudio.yandex.ru/docs/en/ai-studio/concepts/search/),
[Embedding API](https://aistudio.yandex.ru/docs/ru/ai-studio/embeddings/api-ref/grpc/),
and [AI Studio quotas and limits](https://aistudio.yandex.ru/en/docs/ai-studio/concepts/limits).

The initial upload and demonstration runs are owner-only and individually pinned
to exact PR commits. Recovery diagnostics report the
HTTP method, sanitized API route and a validated provider code, without
credentials, object IDs or response messages. Requests go only to Yandex's
`ai.api.cloud.yandex.net` host and use its `/v1` project-routing headers. The runner uses Python's standard library;
it makes no OpenAI service call and adds no SDK or Python dependency.
The fingerprint-based reuse path never overwrites an existing file. Each admitted
run allows at most one new repository file, one Issue snapshot version, one direct
search query and (when enabled) one Yandex model call. The workflow uses the
existing `YANDEX_API_KEY` and
`YANDEX_PROJECT_ID` Actions secrets; provider-side API limits remain authoritative.
For a manual run, choose `vector-store`, enable `allow_vector_store_write`, and
provide the approved reference. To index the tracked repository and generate an
answer, also enable `include_repository` and `allow_model_call`:

```sh
python scripts/semantic_pipeline.py \
  --mode vector-store --corpus tasks --query "симуляция офиса" \
  --allow-vector-store-write --include-repository --allow-model-call \
  --approval-reference owner-approved
```

## Ask the native Logos runtime in GitHub Actions

The existing `RAG work` workflow also accepts `mode=logos`. This checks out the
selected branch, installs the runtime dependencies and calls the same
`LogosClient` used by the application. The question is passed through a UTF-8 file;
the reply comes from the native runtime and its `InvocationContext`,
`ExecutionTrace` and `UniversalToolExecutor` path.

Dialogue instructions allow ordinary knowledge questions as well as repository
work. Repository rules govern code/tool operations; an answer about history or
another general topic does not require evidence from project files.

Choose the branch, enter the question in `query`, and select the canonical
`case_issue` and `case_pr` (defaults: 1413 and 1435). Before generation, the
workflow captures the complete GitHub case and applicable repository guidance,
then attaches that same versioned context to the existing project Vector Store.
The initial prompt includes the full captured case, not just retrieved excerpts.
Preparation fails if required context or its matching indexed receipt is missing.
Reference-case mode records the selected PR's revision separately from the current
checkout. Earlier ChatGPT conversations unavailable to the checkout are not
claimed as included. See [Native Logos quality and context](logos-native-quality.md)
for the exact scope, provenance and acceptance criteria.

The selected model is `deepseek-v4.1-flash`, with Yandex's documented
1,048,576-token context window. The request explicitly asks for reasoning `high`
and 393,216 output tokens; that output value is a compatibility candidate from
DeepSeek upstream, not a confirmed Yandex maximum. Unsupported parameters fail
visibly without automatic reduction or a weaker-model fallback. Temperature 0.3
follows Yandex's code example. `truncation=disabled` prevents silent removal of
early conversation when the input exceeds the provider's context window.

The dialogue enables every registered local tool category through the native
executor, hosted web search with high search context, file search over the prepared
project index, and Code Interpreter. Scoped project readers provide authenticated
GitHub REST and Discussions reads. Declaring these tools does not establish that
each external dependency works; live tool results remain separate evidence.
Existing runtime validation and approvals still apply.

The adapter adds no file-read, file-write or local round-count cap. The request
uses background mode, with a known response ID checkpointed before up to 7,200
seconds of GET polling; the POST transport allowance is 900 seconds. The Actions
job has a 360-minute timeout. Provider limits remain authoritative, and the
unknown maximum number of hosted calls is not replaced by an invented number.
There is no hard currency cap. Provider usage and response identifiers are
recorded when available; unconfirmed cost remains unknown. A failed or timed-out
generation is not automatically retried.

The workflow uses existing Yandex Actions secrets and a temporary encrypted
credential store outside the checkout. GitHub credentials are kept out of the
initial context and exported receipts. This requires no application server,
website or phone.

The `logos-answer-<run_id>` artifact and the `LOGOS_RESULT=` JSON line in the job
log contain the actual reply, status, correlation IDs, capability receipt,
available usage, local tool evidence and recorded hosted-tool calls. They exclude
the credential store and raw trace. A
question about the repository can cause Logos to inspect or work with files;
an ordinary knowledge question may need no tools. Each dispatch runs one dialogue
turn. This workflow does not schedule recurring work or publish repository edits.

The result also reports recorded tool calls by name, call ID and native execution
success. For command tools it includes the available exit code and SHA256 of the
recorded command and stdout, without exposing those strings. Missing evidence
remains unknown; recognizable redaction or truncation prevents reporting an exact
string hash. A model's claim that a build succeeded is not itself tool evidence.

To retrieve an existing answer without another model call, dispatch
`mode=logos-result` and put the earlier run ID in `query`. This job only downloads
that run's answer artifact and writes its JSON to the log. It needs Actions read
access and receives no provider credentials. The artifact's seven-day retention
still applies.

For a provider failure whose response ID was saved, `mode=logos-response` accepts
that UUID in `query`. It uses the native credential resolver for a single GET of
the stored provider response. It creates no conversation and makes no generation
request. A successful read is reported as `retrieved`, independently of the
original `provider_status`. The report exposes symbolic error codes/reasons, not
raw provider messages or payloads. Original dialogue failures also preserve these
diagnostics from their native trace when available. A missing or expired response
is reported as a retrieval failure; it never triggers another generation.

Local invocation requires provider credentials configured separately and GitHub
read access for context preparation and the scoped project readers. Prepare the
context and its matching knowledge receipt before requesting a new generation:

```sh
python -m scripts.logos_context \
  --repo-root . --issue 1413 --pr 1435 --reference-case \
  --owner-context-file docs/agents/logos-native-quality.md \
  --out /tmp/logos-context.json

python -m scripts.logos_knowledge \
  --context-file /tmp/logos-context.json --out /tmp/logos-knowledge.json

python -m scripts.logos_dialogue \
  --question-file /tmp/question.txt \
  --context-file /tmp/logos-context.json \
  --knowledge-file /tmp/logos-knowledge.json \
  --out /tmp/logos-answer.json

python -m scripts.logos_dialogue \
  --response-id <stored-response-uuid> --out /tmp/logos-diagnostic.json
```

The runner's enabled filesystem tools can be audited with
`python -m scripts.logos_tool_probe`. The probe invokes the native
UniversalToolExecutor with approval disabled, checks results against temporary
fixtures and removes them afterwards. It reports positive scenarios, omitted
optional arguments, and provider-advertised nullable arguments separately.
The default run uses a loopback HTTP fixture; `--external` additionally checks a
read-only GET of this public repository through GitHub's API. Disabled categories
are inventoried, not executed. A completed audit can report failed or blocked
tools: its exit code is not an all-tools-pass assertion.
Dispatch `RAG work` with `mode=logos-tools` to run this audit in the same runner
without a model call or provider credentials. The JSON log and answer artifact
contain the measured results; `query` is not required in this mode.

## Later work

A live quality experiment requires separately approved scope/call count/budget.
Freeze the corpus, queries, hidden expected answers, retrieval parameters and
code revision. Measure recall separately from candidate-selection quality,
false confirmations, unsupported refusals, latency and usage. A model downstream
of BM25 cannot recover an excluded candidate.

The broader four-result assessment, contradiction resolution and dependency
invalidation in #1413 remain separate future work; search does not depend on them.
