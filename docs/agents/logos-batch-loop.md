# Пакетный цикл Логоса под правилом Суда (эскиз)

Предложение владельца от 08.11.2026: «designing loop system under court rule so
batch processing can be done and we could run different models in batch». Это
эскиз архитектуры, не реализация. Решения, которые остаются за владельцем,
помечены явно.

## Что уже есть

- **Сервер модели — asmrun на ПК без ОС** (research/asmrun). В памяти 8 ГБ
  помещается одна чат-модель (9B в Q4_K_M) и эмбеддер. Смена чат-модели —
  это выгрузка и загрузка с флешки, ~1 минута на 5–7 ГБ. API: `POST /v1/turn`
  (ход, поток ответа, итог с числами и температурами), `GET /v1/status`,
  `POST /api/embed`. Контекст один с загрузки; `q35_reset` есть в коде, но не
  вызывается.
- **Суд** (docs/agents/logos-court-procedure.md): карточка эпизода с полями
  `episode`, `sources`, `claim`, `fact`, `decision: ALLEGED`, `fix`,
  `verification`, `owner_acceptance`. Решение выносит владелец.
- **Головной запуск по задаче** (agent_runtime/issue_runner.py): Логос без
  интерфейса работает над GitHub-issue в своём чекауте с профилем инструментов
  только для чтения.
- **Инструменты** — категории реестра; локальной модели отдаются `remember`,
  `python`, `filesystem`, `git` (ollama_client/settings.py, TOOLS).

## Цикл

```text
  очередь задач (Kristall)  --->  планировщик  --->  раннер asmrun
  issue / чат / Суд              пакеты по модели     одна модель в памяти
        ^                              |                    |
        |                        карточка эпизода     /v1/turn, инструменты
        +------ Суд: решение <--- отчёт пакета <------ результат, trace
```

1. **Задача** — запись в Kristall: `task_id`, источник (issue, диалог, дело
   Суда), текст поручения, требуемая **модель** (ключ из MODELS), категории
   инструментов, бюджет (ходов, токенов, времени), статус
   (`queued → running → done | failed`), `episode` (ID карточки Суда).
2. **Пакет** — все задачи в очереди с одной моделью. Планировщик берёт пакет,
   просит раннер загрузить его модель, затем ведёт задачи по одной через
   `/v1/turn` с инструментами Логоса; между задачами — сброс контекста
   раннера (нужен новый маршрут `POST /v1/reset`, вызывающий `q35_reset`).
   *Решение владельца:* сброс между задачами противоречит правилу «один
   контекст с загрузки» для чата; для пакетного режима предлагается
   исключение, иначе задачи видят друг друга.
3. **Смена модели** — новый маршрут раннера `POST /v1/model {"name": ...}`:
   выгрузка текущей чат-модели, загрузка названной с флешки (эмбеддер
   остаётся). Планировщик меняет модель только на границе пакетов, чтобы минута
   загрузки окупалась.
4. **Карточка эпизода на каждую задачу**, по процедуре Суда: источники
   (issue, SHA чекаута, trace invocation), что модель сделала (вызовы
   инструментов, диффы, коммиты), `verification: NOT_RUN` (тесты только по
   отдельной команде на GitHub Runner), `decision: ALLEGED`. Отчёт пакета —
   список карточек в деле Суда одним комментарием.
5. **Решение** — владелец в Суде: принять (`owner_acceptance`), отклонить,
   вернуть в очередь с другой моделью. Ничего не публикуется и не сливается
   без этого решения, кроме того, что сама задача делала в рамках прямого
   push в develop по AGENTS.md.

## Границы

- Одна модель в памяти ПК: параллельности нет, есть пакетирование.
- Пакет модели выполняется, пока владелец не пользуется чатом; переключение
  модели ради чата — тоже решение планировщика по приоритету (владелец выше
  пакета).
- Все данные пакета (задачи, результаты, карточки) — и в векторной базе
  (AGENTS.md), эмбеддером того же раннера.
