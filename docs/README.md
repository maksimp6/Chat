## Как читать статус

**Реализовано в коде** означает наличие изменения в указанном коммите. Это не
равнозначно зелёному CI, успешному развёртыванию или готовности всей подсистемы.
**Согласованный контракт** описывает требуемое поведение и должен явно ссылаться
на задачу реализации. **Исторический документ** не задаёт текущую архитектуру.

Текущая база, включённые PR и известные блокеры записываются только в
[интеграционном реестре](integration/current-scope.md). Не копируйте эту таблицу
в обзоры: несколько независимых списков статусов быстро расходятся.

Историческое [ревью окружений #330](architecture/branch-environments.md)
сохранено как указатель на исходный документ. Модель отдельных процессов из
этого ревью не является текущей инструкцией запуска.

## Правила обновления документации

1. Сверяйте описание с конкретным SHA `master`, кодом и тестами; для результата
   запуска указывайте ссылку на run. Комментарий агента не доказывает публикацию.
2. Обновляйте основной документ подсистемы, а из обзорных страниц давайте ссылку.
   Разделяйте фактическую реализацию, принятые требования и будущие идеи.
3. При замене документа оставляйте понятный переход по старому пути. Историю
   решений сохраняйте ссылкой на неизменяемый коммит, не выдавая её за инструкцию.
4. Проверяйте относительные ссылки, блоки кода и команды. Для команды указывайте
   рабочий каталог и предпосылки; не помещайте секреты или реальные токены в пример.
5. Для изменений только Markdown достаточно предметных локальных проверок
   документации. Обязательные проверки GitHub при этом не отключаются, а их
   отсутствие или сбой не объявляются успехом.
