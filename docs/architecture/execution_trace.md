# Execution Trace и расчёт стоимости

## Логическая модель запроса

Один пользовательский запрос считается **одной логической операцией** и получает один `ExecutionTrace`, даже если для его выполнения выполняется несколько последовательных генераций через Yandex Responses API.

Типичный сценарий:

```text
Один пользовательский запрос
  │
  ├─ Responses API #1
  │    └─ модель запрашивает tool call
  │
  ├─ выполнение локального/MCP-инструмента
  │
  └─ Responses API #2
       └─ финальный ответ модели
```

Следовательно, `Responses API #1` и `Responses API #2` не являются двумя пользовательскими запросами. Это последовательные шаги одной операции.

## Usage

Каждый ответ Responses API сохраняет собственный фактический `usage` в `ExecutionTrace`. Эти значения нужны для observability и диагностики каждого шага.

Не следует автоматически складывать `input_tokens`, `output_tokens` или `total_tokens` разных шагов и называть результат количеством токенов одного пользовательского запроса. Последующий вызов может содержать историю диалога, результаты инструментов и другой уже существующий контекст.

В Trace должны отображаться реальные значения `usage` каждого Responses API отдельно.

## Расчёт стоимости

Стоимость пользовательской операции рассчитывается **один раз после завершения всей цепочки**, по `usage` финального Responses API.

Текущая логика:

```text
Responses #1 usage → сохраняется в Trace
Tool execution    → сохраняется в Trace
Responses #2 usage → сохраняется в Trace и используется для расчёта цены
                         │
                         ▼
                    calculate_cost()
                         │
                         ▼
                    total_cost
```

Если инструментов нет и выполняется только один Responses API, его `usage` одновременно является финальным `usage` операции.

Важно: стоимость не должна складываться между промежуточными шагами только на основании того, что в Trace присутствует несколько объектов `responses`. Правило стоимости определяется финальным `usage` логической операции.

## Временные интервалы

Временные границы Responses API в Waterfall должны отражать фактическое выполнение, а не вычисляться как интервал от окончания предыдущего шага.

Для каждого Response предпочтительны реальные `start_timestamp` и `end_timestamp`, записанные во время выполнения. Визуализатор не должен выдавать такой интервал за фактический, если он был восстановлен только по косвенным данным.

События инструментов остаются мгновенными событиями/интервалами их фактического выполнения и могут пересекаться с другими элементами Trace.

## Ошибки доступа к моделям

HTTP `403 Forbidden` от Yandex Responses API необходимо отличать от ошибки выполнения инструмента.

Пример фактической ошибки:

```text
403 Forbidden
No permission 'use_model' to model gpt://<PROJECT_ID>/alice-lite/latest
```

Такая ошибка означает, что запрос к API был отклонён на уровне **права использования модели** (`use_model`). Сам по себе этот ответ не доказывает, что модель не поддерживает `tools` или function calling. Нельзя автоматически делать вывод о несовместимости модели с инструментами только по такому `403`.

При ошибке модели Trace должен сохранять как минимум:

- HTTP status;
- модель/model URI;
- URL или endpoint запроса;
- текст `detail` из ответа API;
- время начала и окончания запроса;
- номер шага Responses API, если запрос является частью многошаговой операции.

Ошибку нельзя терять в общем `HTTP 500`: внутренний ответ приложения может быть `500`, но исходная причина и параметры ошибки Yandex должны оставаться доступны в Execution Trace.

## Модели и доступ

Наличие модели в интерфейсе Model Gallery не следует считать доказательством того, что текущий проект или сервисный аккаунт имеет право её использовать. Перед использованием конкретного `model URI` необходимо учитывать доступ проекта к модели.

В частности, внутренний ключ Alice Pro `alice-lite` и название `YandexGPT Lite` из каталога Yandex AI Studio нельзя считать эквивалентными без подтверждения соответствующего `model URI` и доступа проекта.

Если API возвращает `No permission 'use_model'`, сначала проверяются модельный URI и права доступа. Проверка поддержки tools выполняется отдельно и только по документации/API-возможностям конкретной модели.

## Тарификация инструментов

По правилам тарификации Yandex AI Studio токены инструментов учитываются отдельно для встроенных инструментов AI Studio. Результаты пользовательских функций в эту категорию токенов не входят.

Следовательно, Trace должен позволять отличать:

- токены модели;
- токены встроенных инструментов, если они применимы;
- выполнение пользовательских local/MCP tools;
- ошибки авторизации модели.
