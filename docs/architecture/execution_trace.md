# Execution Trace и расчёт стоимости

Описание текущего кода сверено с `master`
`de8f97c8342c8c073c84885bf8f301bba5692b33`.
Раздел о `make_snapshot()` и новом `finalize()` ниже является **согласованным
контрактом задачи [#401](https://github.com/maksimp6/Chat/issues/401)**, а не
заявлением, что этот контракт уже реализован.

## Одна операция, несколько шагов

Один пользовательский запрос получает один `ExecutionTrace`. Внутри него могут
быть несколько вызовов Responses API, polling, local/MCP-инструменты и ошибки.

```text
Запрос пользователя -> один trace
    -> Responses API: шаг 1
    -> инструмент
    -> Responses API: шаг 2
    -> итоговый ответ
```

Фактический `usage` сохраняется для каждого ответа провайдера. Сумма usage разных
вызовов описывает обработку на этих вызовах, а не количество уникальных токенов
в диалоге: повторно переданный контекст может учитываться на нескольких шагах.

## Текущий биллинг в коде

Источники: [trace_manager.py](../../trace_manager.py),
[billing.py](../../billing.py), [config.py](../../config.py).

`_update_billing_for_response()` создаёт или заменяет AI-позицию по ключу
`(step, response_id)`. Повторный polling того же ответа обновляет эту позицию,
а не должен образовывать ещё одно начисление за тот же response. При отсутствии
устойчивого `response_id` вызывающий код обязан особенно внимательно сохранять
идентичность шага; нельзя обещать дедупликацию произвольных неидентифицированных
ответов.

`build_ai_billing_item()` использует `usage` и тариф модели из `ALL_MODELS`.
`aggregate_billing()` суммирует зарегистрированные позиции. **Правило «считать
только последний Responses API» не описывает эту реализацию.** Несколько
самостоятельных вызовов модели и несколько снимков одного вызова необходимо
различать.

| Поле / статус | Значение в текущей реализации |
| --- | --- |
| `items` | Позиции отдельных зарегистрированных ответов |
| `total_cost` | Сумма известных позиций со статусом `calculated` |
| `unknown` | Для позиции не найден настроенный тариф; стоимость `None`, не подтверждённый ноль |
| `partial` | В агрегате есть неизвестные позиции; известная сумма не является полной стоимостью |
| `calculated` | Расчёт выполнен по локальной конфигурации; это не подтверждение счёта провайдера |
| `currency`, `pricing_version` | Сейчас `RUB` и `config-v1` |
| Округление | Стоимости округляются до шести знаков в существующем коде |

Тарифы в конфигурации требуют отдельной сверки с провайдером. Эта страница не
утверждает актуальность цен и не вводит плату за условные CPU/tool/API-секунды.
Вычислительный биллинг из отдельной ветки Claude нельзя считать вошедшим в
`master` только потому, что он опубликован в той ветке.

## Текущая финализация и её ограничения

Существующий `finalize()` фиксирует общую длительность при первом вызове,
повторно агрегирует текущий `billing.items` и возвращает сериализованное
представление. Это ещё не терминальный неизменяемый снимок из контракта #401:
флаг завершения устанавливается до окончания сборки результата.

[trace_mirror_integration.py](../../trace_mirror_integration.py) устанавливает
обёртку над `finalize()` и делает best-effort попытку зеркалирования. Это
существующий побочный эффект, который при рефакторинге нельзя незаметно
перенести в метод чтения `make_snapshot()`.

## Согласованный контракт #401

### Общая сборка

Оба метода используют один внутренний сборщик, условно
`_build_snapshot(...)`. Он заново получает позиции и итоги из первичных фактов:
ответов, usage, измерений и выбранной версии тарифа. Предыдущие снимки и уже
вычисленные итоги не становятся дополнительными исходными расходами.

### make_snapshot()

Возвращает независимую глубокую копию текущего состояния. Не меняет исходные
события, расходы или статус; не сохраняет данные, не вызывает mirror и не
проводит расход в казначействе. После завершения возвращает копию зафиксированного
финального результата.

### finalize()

Первый вызов использует окончательную границу завершённой работы, пересобирает
полный итог, проверяет согласованность и только после успешной сборки атомарно
фиксирует результат, время и статус.

Сбой сборки не оставляет trace наполовину завершённым. Повторный вызов возвращает
независимую копию зафиксированного результата без новых начислений, изменения
длительности или повторной фиксации. Конкурентные вызовы не должны обходить эту
гарантию.

После финализации изменения исходных фактов должны отклоняться явно, а не молча
теряться. Поздняя корректировка требует отдельной явно связанной операции, а не
незаметного изменения уже проведённого итога.

### Равенство биллинга

Для завершившейся работы при неизменных первичных фактах:

```python
snapshot = trace.make_snapshot()
finalized = trace.finalize()
assert snapshot["billing"] == finalized["billing"]
assert trace.make_snapshot()["billing"] == finalized["billing"]
assert trace.finalize()["billing"] == finalized["billing"]
```

Это пример требуемого контракта, не готовая команда для текущего `master`.
Сравнивается весь billing: позиции, usage, измерения для тарификации, тарифы,
округление, промежуточные суммы, валюта и итог.

**Время чтения не является новой оплачиваемой работой.** Если между snapshot и
finalize ничего не выполнялось, движение часов само по себе не должно менять
billing. Для этого оба расчёта используют одну границу оплачиваемой работы из
зафиксированных измерений и одну версию тарифа, а не два независимых значения
`now()`. Метаданные времени просмотра можно хранить отдельно от billing.

Пока операция действительно выполняется, новые измерения могут менять
предварительную оценку. Такой снимок не является последним снимком завершённой
работы; его нельзя выдавать за окончательный проведённый расход.

### Измерения вычислительных ресурсов

Нельзя называть `wall_time - api_time` измеренным CPU-временем. Там могут быть
ожидание и работа инструментов. CPU-измерение должно быть атрибутировано именно
этой операции; общепроцессное измерение также может включать другие runtime.
Для wall-time используйте честное название и определённые границы интервалов.
Одно выполнение не должно дважды попадать в пересекающиеся категории.

### Сохранение и проведение расхода

Финальный расчёт, сохранение trace, mirror и финансовое проведение являются
разными операциями. Их повторные доставки требуют собственных ключей
идемпотентности, а не добавления стоимости внутри getter.

Сейчас `settle_billing_to_treasury()` проверяет полноту стоимости и владельца,
использует reference `billing:<trace_id или invocation_id>` и различает
`posted`, `already_posted` и `skipped`. Не меняйте trusted owner на значение,
пришедшее от клиента, ради прохождения проверки.

## Проверки контракта

- Сто одинаковых snapshot не меняют живой trace и не добавляют позиции.
- Последний snapshot и первый finalize имеют строго одинаковый billing;
  тест продвигает часы без новой работы, а не только замораживает `now()`.
- Повторные и конкурентные finalize не меняют итог и не удваивают compute-плату.
- Изменение вложенных данных возвращённой копии не меняет trace или другую копию.
- Сбой финальной сборки оставляет возможность корректного повторного завершения.
- Запись после финализации отклоняется явно; polling не дублирует тот же response.
- Неизвестная цена остаётся неизвестной; snapshot не вызывает запись, mirror
  или settlement; существующий учёт AI-usage сохраняется.

Эти проверки являются критериями реализации #401. Их перечисление в Markdown
не означает, что соответствующие тесты уже добавлены или прошли.

## Ошибки, интервалы и безопасная диагностика

Сохраняйте фактические начала/окончания вызовов, `step`, `call_id`, `parent_id`,
исходный HTTP status и безопасный текст ошибки. Восстановленный интервал не
выдаётся за измеренный. Ответ `403` с `No permission 'use_model'` указывает на
ошибку доступа к указанной модели и сам по себе не доказывает несовместимость
модели с tool calling.

Не помещайте в trace ключи, bearer-токены, cookies, пароли и приватные URL с
секретным префиксом. Ошибка внешнего mirror не должна превращаться в ошибку
основного пользовательского запроса.
