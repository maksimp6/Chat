# Границы архитектурной интеграции

Этот документ отвечает за распределение ответственности между подсистемами.
[Реестр интеграции](../integration/current-scope.md) отвечает за датированный
статус PR, проверок и блокеров. Не поддерживайте второй список кандидатов здесь.

Архитектурные решения ведутся в
[#350](https://github.com/maksimp6/Chat/issues/350), общая координация в
[#343](https://github.com/maksimp6/Chat/issues/343), staging в
[#351](https://github.com/maksimp6/Chat/issues/351).

## База работы

Начинайте с актуального `master`, фиксируя его SHA до изменения файлов.
Исторический коммит объединения runtime-фундамента #363 не является постоянной
базой для новых веток. Перед публикацией и принятием проверяйте изменения базы.

Продолжайте существующий PR, если он владеет той же работой. Не открывайте новый
PR вместо исправления существующего только из-за неудачного push или красного
CI. Отдельный PR оправдан независимой областью изменений.

## Обязательные границы

| Компонент | Ответственность | Что нельзя переносить в соседний слой |
| --- | --- | --- |
| `EnvironmentManager` | Метаданные, worktree и жизненный цикл runtime | Второй процесс/контейнер на каждое preview |
| `RuntimeLoader` | Ограниченная загрузка выбранной ревизии | Изменение общих `sys.path`, `sys.modules` и переменных окружения |
| `RuntimeDispatcher` | Привязка runtime, owner и доступа к общим ресурсам | Прямой доступ к чужой БД, файлам или глобальному executor |
| `UniversalToolExecutor` | Политика и исполнение инструментов | Независимый обход прав через MCP, плагины или агентов |
| `InvocationContext` / `ExecutionTrace` | Корреляция и наблюдаемость | Отдельная несвязанная история каждого адаптера |

Потоки не изолируют враждебный код. Ограниченный loader нельзя описывать как
песочницу общего назначения. Политика runtime остаётся в
[основном контракте](../runtime/runtime-dispatcher-policy.md).

## Устранение пересечений

- MCP-маршрутизация и изоляция инструментов используют один путь через диспетчер
  и executor. Исторические изменения #361/#370 не должны порождать две версии
  реестра инструментов в следующих PR.
- Storage владеет интерфейсом провайдера, filesystem-слой владеет ограничениями
  пути и runtime root. Изменения после #366/#378 не должны создавать обход
  файловой изоляции через storage-адаптер.
- Агент диалога определяет идентичность и маршрутизацию, плагин предоставляет
  возможности через контракт исполнения. Продолжение #369/#377 не создаёт
  отдельную систему полномочий или второй цикл исполнения инструментов.
- Биллинг собирает стоимость, казначейство проводит расход. Получение снимка
  trace не должно ни сохранять его во внешние сервисы, ни проводить расход.
  Согласованный контракт #401 описан в [документе trace](execution_trace.md).

При конфликте выбирайте реализацию, сохраняющую согласованную границу, а не
механически объединяйте обе. Причину замены фиксируйте в PR и реестре.

## Приёмка изменения

1. Укажите base/head SHA, затронутую подсистему и зависимости.
2. Проверьте фактический diff и выполните проверки, относящиеся к изменению.
   Для Markdown это ссылки, команды, структура и соответствие коду; для runtime
   дополнительно нужны поведенческие проверки изоляции и жизненного цикла.
3. Проверьте обязательный CI на конечном SHA. Успешная локальная проверка,
   `mergeable`, `skipped` и отчёт агента не заменяют результат CI.
4. Ошибку общей базы исправляйте в её владельце, не размножая одинаковые патчи
   по всем PR. Не ослабляйте проверки ради зелёного индикатора.
5. Сохраняйте совместимость SQLite/PostgreSQL при изменении схемы, границы
   подписи Android и серверное хранение секретов.
6. Публикуйте реальные коммиты и PR. Слияние требует принятия пользователем и
   соблюдения правил репозитория; реестр не даёт разрешения на автослияние.

Не восстанавливайте удалённые root-артефакты, `runtime_marker.txt`, старый
localhost-прокси или отдельные Flask-процессы при разрешении конфликтов.
История решения доступна в Git, но не отменяет принятую архитектуру.
