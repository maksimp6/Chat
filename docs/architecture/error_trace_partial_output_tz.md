# ТЗ: Трейсинг ошибочных сообщений и сохранение частичного вывода модели

## 1. Цель

Если обработка одного пользовательского сообщения завершается ошибкой после того, как модель уже успела сформировать какой-либо результат, пользователь не должен терять этот результат.

Каждый такой запрос должен оставаться полностью диагностируемым через `ExecutionTrace`.

Главный принцип: **ошибка не должна уничтожать уже полученный результат модели и не должна уничтожать Trace**.

---

## 2. Ожидаемое поведение

### 2.1 Модель ничего не успела сгенерировать

Пользователь получает:

```text
⚠️ Ошибка: <текст ошибки>
```

У сообщения доступен `ExecutionTrace`.

### 2.2 Модель успела сгенерировать текст, после чего pipeline упал

Пользователь получает одно assistant-сообщение:

```text
<текст, который успела сгенерировать модель>

⚠️ Ошибка: <текст ошибки>
```

У этого же сообщения доступен `ExecutionTrace`.

При повторной загрузке истории результат должен остаться таким же, то есть частичный вывод должен быть сохранён в БД, а не только собран браузером из Trace.

### 2.3 Модель сформировала несколько Responses API

Нужно определить **последний релевантный непустой текст модели**, относящийся к завершившемуся запросу.

Нельзя бездумно склеивать промежуточные ответы, если это приводит к дублированию текста.

`ExecutionTrace.responses[]` при этом должен сохранять все Responses API как есть.

---

## 3. Backend

### 3.1 ExecutionTrace

`ExecutionTrace` является источником диагностических данных.

Он должен сохранять:

- все Responses API;
- полный `raw` ответа;
- `step` каждого Responses API;
- реальное время начала запроса;
- реальное время получения ответа;
- `timing_ms`;
- tool calls;
- ошибки pipeline;
- Python exception state, если он доступен;
- API request payload;
- события выполнения.

Уже существующие поля Trace не удалять и не ломать.

### 3.2 Извлечение частичного результата

На backend должна быть единая функция/метод для извлечения текста из сохранённых Responses API.

Нельзя дублировать отдельный упрощённый parser только во frontend.

Функция должна:

1. пройти по `trace.responses`;
2. рассмотреть `response.raw`;
3. извлечь текстовые output items Responses API;
4. игнорировать tool/function call как пользовательский текст;
5. корректно обработать отсутствие текста;
6. вернуть последний релевантный непустой результат.

Если в проекте уже существует `extract_reasoning_and_text()`, использовать его или вынести общую логику так, чтобы не появилось двух расходящихся parser-ов.

### 3.3 Обработка исключения `/api/chat`

При исключении pipeline:

1. завершить `ExecutionTrace`;
2. записать ошибку в Trace;
3. определить, есть ли уже полученный результат модели;
4. сформировать пользовательский `reply`:
   - если результата нет: ошибка;
   - если результат есть: результат + ошибка;
5. сохранить именно этот текст как assistant message в БД;
6. вернуть этот же `reply` и `trace` в JSON response.

HTTP статус ошибки можно сохранить корректным для API, но frontend не должен терять `reply` и `trace` из-за статуса.

Рекомендуемый ответ:

```json
{
  "error": "<error>",
  "reply": "<partial output>\n\n⚠️ Ошибка: <error>",
  "partial_output": "<partial output>",
  "trace": { ... }
}
```

Если частичного вывода нет:

```json
{
  "error": "<error>",
  "reply": "⚠️ Ошибка: <error>",
  "partial_output": null,
  "trace": { ... }
}
```

---

## 4. Frontend

`chat.js` должен нормально обрабатывать error response, содержащий:

- `error`;
- `reply`;
- `partial_output`;
- `trace`.

Frontend должен показывать `reply` и передавать `trace` в существующий UI сообщения.

**Запрещено** превращать HTTP `4xx/5xx` в искусственный HTTP `200` через глобальный monkey-patch `window.fetch`.

Файл `static/trace_error_message.js` из текущей реализации PR #2 после переноса логики на backend должен быть удалён, если его функциональность больше не нужна.

Не менять поведение успешных `/api/chat` запросов.

---

## 5. Persistence

После ошибки и перезагрузки страницы пользователь должен видеть сохранённое assistant-сообщение с частичным результатом, если он был.

Trace должен быть доступен из сохранённого сообщения.

Нельзя рассчитывать на то, что браузер повторно извлечёт текст из Trace после reload.

---

## 6. Execution Trace Viewer

Для ошибочного сообщения Trace должен открываться так же, как для успешного сообщения.

Trace Viewer должен позволять увидеть:

- Responses API шаги;
- request payload;
- response `raw`;
- timing;
- tool calls;
- события;
- ошибку;
- Python traceback и locals, если они были захвачены.

Ошибочный запрос не должен превращаться в отдельный безымянный лог вне общей модели Trace.

---

## 7. Timing

Для Responses API использовать реальные интервалы:

```text
start_timestamp = фактическое начало API request
end_timestamp   = фактическое получение финального response
```

Не вычислять начало следующего Responses API через конец предыдущего.

Tool execution должен использовать собственные реальные `start_timestamp` / `end_timestamp`.

Существующую реализацию корректных timestamp не ломать.

---

## 8. Безопасность

При сохранении traceback и locals нельзя раскрывать:

- API keys;
- authorization headers;
- passwords;
- tokens;
- cookies;
- другие очевидные секреты.

Существующую redaction-логику сохранить и расширять только при необходимости.

---

## 9. Cost / usage

Наличие ошибки не должно менять существующую модель биллинга.

Если Responses API успел вернуть usage, он должен оставаться в Trace.

Стоимость логического пользовательского запроса рассчитывается по существующей принятой схеме проекта, а не путём случайного суммирования всех промежуточных Responses API.

---

## 10. Acceptance criteria

Задача считается выполненной, если проходят все сценарии:

### A. Ошибка до ответа модели

- assistant message отображает ошибку;
- Trace доступен;
- Trace содержит ошибку;
- после reload всё сохраняется.

### B. Ответ модели + последующая ошибка

- текст модели отображается;
- ниже отображается ошибка;
- Trace доступен на том же сообщении;
- после reload текст модели не исчезает;
- Trace содержит Responses API и ошибку.

### C. Несколько Responses API

- все Responses API присутствуют в Trace;
- пользователь не получает бессмысленного дублирования промежуточного текста;
- отображается последний релевантный непустой результат.

### D. Tool call + ошибка

- tool call присутствует в Trace;
- его аргументы и результат/ошибка сохраняются;
- если до ошибки был текст модели, он не теряется;
- Trace доступен после reload.

### E. Успешный запрос

- существующее поведение не изменилось;
- обычный reply отображается как раньше;
- Trace продолжает работать;
- timings не сломаны.

### F. Архитектура

- нет глобального monkey-patch `window.fetch` для преобразования HTTP ошибок в `200`;
- логика извлечения partial output находится на backend/в общей Trace-логике;
- нет второго независимого parser-а Responses output во frontend.

---

Текущий PR #2 содержит frontend workaround `static/trace_error_message.js`, который перехватывает `window.fetch` и нормализует ошибочный ответ в HTTP `200`.

Этот подход считать промежуточным и заменить на backend-реализацию из данного ТЗ.

После реализации:

1. удалить `static/trace_error_message.js`;
2. изменить обработчик исключений `/api/chat`;
3. изменить frontend error handling так, чтобы он сохранял `reply` и `trace` из error response;
4. добавить тесты на partial output;
5. проверить успешный и ошибочный сценарии;
6. проверить persistence после reload.
